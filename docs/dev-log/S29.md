The worker runs many shots at once from several threads. S29 gives the Jobs module one safe place to take a job and write each step, so the page always shows the truth. It replaces the S01 stubs in the Jobs worker interface: `claimNextJob`, `recoverInterrupted`, `setShotState`, `setShotPhoto`, `startAttempt`, `finishAttempt`, `setShotResult`, `finishJob`, `stopJob`. It also writes the measurement records `started_at`, `deadline_at`, `finished_at`, `first_finished_at` and `total_cost_usd`. It was built against seeded synthetic rows. ## What was built

- `app/jobs/shot_writes.py` (new). Shot and attempt writes: `set_shot_state`, `set_shot_photo`, `start_attempt`, `finish_attempt`, `set_shot_result`, plus `now_utc`, `iso`, `MAX_ATTEMPTS = 4`, `IN_FLIGHT`, the `NEXT` state-rule table. Each write is one short transaction that starts with a no-op `UPDATE ... RETURNING` on a shot of a running job (`_lock_shot`). That takes SQLite's write lock, serialises the writer against stop and finish, and raises `JobNotRunning` once the job is no longer running (`LookupError` for an unknown shot).
- `app/jobs/worker_interface.py` (rewritten). `claim_next_job` is one conditional `UPDATE ... RETURNING` that takes the oldest queued job (by `submitted_at`, then `created_at`, then `id`) only if no job is running. It sets `started_at` and `deadline_at` (+30 minutes) and clears `finished_at` and `stop_reason`. It returns a `Job` with only its pending, non-removed shots. Also `_stop`/`stop_job`, `recover_interrupted`, `finish_job` (locks first, refuses early ready, bumps `video_version`, keeps the first `first_finished_at`, totals cost from `provider_calls`), and re-exports of the five shot writes.
- `tests/support/worker_rows.py` (new): synthetic raw-SQL seeds.
- `tests/jobs_worker/conftest.py`, `test_shot_writes.py` (22 tests), `test_job_runs.py` (20 tests): 42 tests in all.

No file shared with S09, S10 or S11 was edited. `provider_calls` is only read. The table-ownership gate stays green.

## Key decisions and assumptions

- Single-writer safety comes from putting a write first in every transaction. Python's sqlite3 (legacy transaction mode) starts BEGIN before DML, so the first statement takes the write lock. The unique running-job index and the `attempt_no` 1 to 4 and unique `(job_shot_id, round, attempt_no)` constraints stay as database backstops. A probe with 4 threads over 20 trials gave one winner each time.
- Four attempts per round (1 try plus 3 regenerations), as in the story and ARCHITECTURE.
- After a job leaves `running`, every write for it raises `JobNotRunning`, including a second `finishJob` or `stopJob`. The finishJob call that ends a running job is allowed.
- A failed shot's detail for `flagged_every_attempt` is exactly the last check's notes. Provider errors reach the shot in the same transaction as the attempt (RL-1).
- `finishJob('ready')` is refused while any non-removed shot is pending or in flight, or failed or skipped (use `ready_with_failures`). A refusal rolls back.
- `first_finished_at` is set only by a ready or ready-with-failures finish. A stopped run delivers no video, so it does not set it (assumption).
- `stopJob` and `recoverInterrupted` fail pending and in-flight shots with `job_stopped` and mark their running attempts `error`.
- The "score" in criterion 12 is the check's `ai_score`; `match_score` is stored too.
- `getJob` belongs to S10 and was not on this branch. Criteria 4, 5, 9 and 12 are therefore asserted on the columns `getJob` maps 1:1 (and the attempts rows). The shared `Job` type has no per-attempt score or cost, no `first_finished_at` and no video version. The story reviewer later probed `queue.get_job` once S10 was on the base branch and confirmed the same values.
- No shared type or INDEX architectural issue was changed.

PRD overrides: none. The PRD says nothing about attempts, queueing, budgets or cost totals.
