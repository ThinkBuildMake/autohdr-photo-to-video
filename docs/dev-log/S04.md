# S04 dev log: Files go to and from a private bucket through short-lived links

## Summary

S04 replaces the Files stub with a real bucket client. Photos, clips and videos are too big for the app to carry, so the browser sends and receives them directly through signed links, and the bucket stays private.

It builds:
- the Files interface `presign_upload`, `presign_download`, `put`, `get`, `head_object` (re-exported from `app/files/service.py`);
- the bucket key layout (`photoshoots/`, `jobs/`, `songs/`);
- the Files "Must hold" rules: the bucket is private (no ACL, no public policy) and presigned links are never logged;
- a reusable `bucket` test fixture on moto that also refuses presigned upload forms the way S3 does (see decisions).

Requirements: DE-2. Supports: FR-1.1, FR-1.9 (shown in S20 and S22). Guards: DE-2. Kind: module. Size: M. Blocked by: S01. Review gate: agents.

**Status:** landed by agents. The story gate (`bash scripts/gate.sh`) passed with 216 tests, ruff clean. No blocking review findings; 3 + 6 minor findings are listed below. No human demo is needed for this story (review gate: agents; any orchestrator demo run is recorded separately).

## Key decisions and assumptions

- **s3v4 and virtual-host addressing are set explicitly.** Without `signature_version='s3v4'`, boto3 signs the POST form with the old scheme (no `x-amz-signature` field). Railway buckets use virtual-hosted URLs at `https://t3.storageapi.dev`.
- **The bucket stays private by construction.** `put` passes only a ContentType and never an ACL; Files sets no bucket policy. Every browser read or write is a presigned link.
- **Links are never logged.** There are no logging calls in `app/files`, and no link goes into an exception message. Log scrubbing (S02) is not depended on.
- **Moto differs from the docs (the one doc/reality difference).** STACK section 14 names moto as the bucket test double, but moto 5.2.4 stores a presigned POST body without reading its policy: an expired form, an oversize file and a wrong Content-Type all returned 204. Presigned GET expiry is not enforced either. Decision (no-questions rule): the `bucket` fixture wraps `S3Response._bucket_response_post` with a policy check that does what S3 does (SigV4 policy signature, expiration, content-length-range, eq/starts-with conditions) and refuses with 403 AccessDenied. Criterion 2 and the DE-2 guard are therefore checked against this test-side enforcement; whether Railway itself enforces it stays ARCHITECTURE open question 6 (checked in S20).
- **Criterion 3 checks the hour through the signed `X-Amz-Expires=3600`**, not by waiting an hour, because moto does not enforce GET expiry.
- **"16 minutes ago" is simulated** by patching `botocore.signers.get_current_datetime` while the link is made (no freezegun). A 14-minute control (accepted, 204) shows the 403 comes from expiry, not a broken signature.
- **Units:** "25 MB" and "1 MB" are tested as 25 MiB (26214400) and 1 MiB (1048576). This is at least as strict; the limit is a caller argument (`max_bytes`), so Photoshoots (S08/S20) picks the unit.
- **Tests never reach a real host.** The `bucket` fixture sets `BUCKET_ENDPOINT=https://s3.us-east-1.amazonaws.com` per test via monkeypatch (moto intercepts AWS hosts only; a `t3.storageapi.dev` client inside `mock_aws` would go to the real network). It is never set globally and never a constant under `app/`, so the approved-hosts gate stays green.
- **Tests use `requests`**, which moto intercepts (not httpx); it was already in the lock as moto's dependency. No new dependency.
- **Test data is synthetic**: a Pillow JPEG padded to 1 MiB and 3 MiB of `os.urandom`, generated in `tmp_path`; no media is committed.

PRD vs docs: the PRD (`docs/AutoHDR Photo to Video.pdf`) does not specify bucket mechanics, so no place in this story needed it to override the docs or the wireframe. The only docs-versus-reality difference is the moto behaviour above.

## Found late and follow-ups

Nothing blocking was found late. Follow-ups, none done in S04:

- **Real bucket check (S20):** whether Railway enforces `content-length-range` and the Content-Type condition on presigned POST (ARCHITECTURE open question 6), and what code HEAD of a missing key returns there (403 versus 404). Photoshoots.completeUpload's size check and delete is the fallback.
- **A delete operation:** Files has no delete in its contract, so S08/S20 will need one (outside this story).
- **Docs:** STACK section 14 and the ARCHITECTURE Files "Test double" note should say that moto does not enforce presigned POST policies or GET expiry, and that `tests/support/bucket.py` does the policy check.
- **Units:** Photoshoots (S08/S20) should pick one unit for the 25 MB limit.
- **Hardening (optional, minor):** strip control characters from attachment names and fall back to the key's basename; guess the content type from the key first; validate `song_key` ext and ids; skip the policy wrapper for `POST /?delete` and refuse unknown operators; add the bare download signature to the logging test; derive the fixture secret from settings; tie the client cache to the settings cache.
- moto accepts unsigned anonymous PUTs (200) where real S3 refuses them; no criterion covers unsigned writes, so this is untested here.
