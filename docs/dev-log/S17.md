# S17 - The editor lets the photographer swap, change or remove shots and re-export

**Kind:** module (M) | **Blocked by:** S01 | **Review gate:** agents
**Status:** landed by agents (no human demo). Story gate green after the round 3 fixes: 675 passed, 5 skipped.

## Summary

Small fixes should not mean starting over. S17 builds the Editor screen (`/jobs/{id}/edit`). It shows a timeline of the shots over the song bar. Each shot has a form to swap its photo or change its movement (the 12 names), speed, movement prompt, photo edit, length or transition, and a button to remove it or put it back. Each card says whether the shot will be made again, only re-cut, or is unchanged. "Re-export video" sends the edits to be made and opens the Job page. A queued or running job opens with every control disabled and "This video is being made".

The fixes after round 1 also changed S11's editShot route: a shot removed and put back with nothing else changed since the last video now answers "unchanged".

## What was built

Only the editor's own files were changed, plus S11's `app/jobs/edits.py` and `app/jobs/reading.py` for fix 1. `app.css` and `base.html` are untouched, so the screen stories built in parallel (S15, S16 and S18) merge cleanly.

- `app/web/pages/editor.py`: loads the job (`queue.get_job`) and its photoshoot (`photoshoots.get_photoshoot`) through the module attributes. It passes the busy flag (`queued` or `running`), the 12 movement display names (`MOVEMENT_LABELS`, PRD pp. 8–9) and their starter prompts (`plan_rules.MOVEMENTS`). A missing job or photoshoot shows the message with its status.
- `app/web/templates/editor.html`: the wireframe's editor, with these parts:
  - "Edit the video" and "Back to the video";
  - the song bar, with one block per shot;
  - timeline tiles (room, "Shot n", movement, "length · change");
  - one form per shot: "Swap the room (photo)", "Camera movement", Speed, Length, "Transition in", "Movement prompt", "Photo edit", and "Remove this room from the video" / "Put this room back";
  - "Re-export video" and its note.
  Every control sits in one `<fieldset>`, which is `disabled` for a busy job.
- `app/web/static/editor.js`:
  - Picking a tile shows that shot's form.
  - Each field saves when it changes, sending only that field. All saves go through one queue, in order.
  - A reply updates the tile, the song bar (block widths follow each shot's length; a removed block is hidden, so the gap closes), the total and the export note.
  - An error shows next to the field that was sent.
  - Re-export disables itself, waits for every queued save, refuses while any field shows an error, and then posts.
  - A failed save puts the form back only when no later save of the same field is queued. A failed movement save also leaves the prompt alone when a prompt save is queued, and does not clear its error until the form shows the server's movement and prompt. A successful answer sets those two fields from the reply when nothing newer is queued. One thrown save is logged and the queue continues.
- `app/web/static/editor.css`: page-specific styles using the wireframe's colours (`#0f6b66`, `#1d2321`), its cards, buttons, banner, song bar stripes and tiles.
- `app/jobs/reading.py`, `app/jobs/edits.py` (fix 1): `removed_in_run`, the put-back rule and the export check (see below).
- `tests/e2e/test_editor_page.py`: 27 Playwright tests. Most stub the four operations in the in-process live server. Remove and put back run through the real routes against seeded rows.
- `tests/jobs_edits/test_edit_shot.py`: 4 route tests for removal and put back.
- `docs/ARCHITECTURE.md`: the `editShot` data-flow row and the `job_shots.edited_at` column now describe the put-back rule.

## Key decisions and assumptions

- **Server-rendered page, JSON edits.** The page is Jinja2 like every other page. Edits are `fetch` calls to the real editShot and exportJob routes. The tests stub `queue.get_job`, `photoshoots.service.get_photoshoot`, `edits.edit_shot` and `edits.export_job` at the module seam, so the real routes, page and browser code all run. S24 swaps in the real modules, and the page does not change.
- **One field per save.** The error format carries no field name, so the message goes next to the field that was sent.
- **The card follows the server.** The card label comes from the reply's `removed` and `pendingChange`. The client never guesses.
- **A movement change also sends that movement's starter prompt.** The clip prompt is built from `movement_prompt`, not the movement name (`app/pipeline/prompt.py`). If the save is refused and no newer movement or prompt save is queued, the saved movement and prompt are put back and the error is cleared. A queued prompt edit is left in place, and the next successful answer writes the server's movement and prompt into the form.
- **The hint says speed makes a new clip,** following INDEX architectural issue 8. The wireframe leaves speed out of the hint.
- **Orchestrator decision (round 1, option 1): keep criterion 6 and fix S11's route.** No schema change; `edited_at` carries the state:
  - Removing or putting back a shot no longer sets `edited_at`; only a field change does.
  - Queuing a run again (`_requeue`: restart, redo, export) sets every removed shot's `edited_at` to the run's `submitted_at`. `reading.removed_in_run` reads that as "left out of the last video".
  - A kept shot is `recut_only` if it was field-edited since the run, or if it was left out of the last video (so putting it back changes the video).
  - exportJob also counts a removed shot that is not `removed_in_run` (removed since the last video) as a change.
  - The result:
    - remove then put back with nothing else changed → `none`, and export answers `nothing_to_export`;
    - remove then export → accepted;
    - put back a shot left out of the last video → `recut_only`;
    - remove, change the length, put back → `recut_only`.
  - A new column was rejected because `init_db` uses `create_all`, which would not add a column to an existing database.
- PRD vs docs: no place where the PRD overrode the docs or the wireframe. No new read was needed: getJob and getPhotoshoot are both in ARCHITECTURE.

## Found late / follow-ups

- **S24:** list only photos with status `uploaded` in "Swap the room (photo)". editShot refuses the others with `invalid_edit`.
- **S24:** a draft or stopped job opens as editable, and every edit answers 409 `not_finished` next to the field. Disable it up front with a message, like a busy job.
- **Wireframe:** the preview card shows only the clip. Add the original photo (`thumbUrl` from getPhotoshoot) beside the edited first frame; the contract has no edited-frame URL yet.
- **Shared movement names:** `MOVEMENT_LABELS` lives in the editor page. Move it to a shared place if the shot-plan cards (S15) need the names.
- A failed save's message blocks Re-export until that field is saved again, when the form still shows the rejected value. If the message is on a shot whose form is hidden, only the note says so; the tile is not marked. A rejected movement is put back and its error is cleared, so it does not block.
- The tile's movement label and room label, and the card heading's room, come from the template and never update until the page is reloaded.
- Editing a removed shot that was already left out of the last video still allows an identical re-export. `export_job` counts `edited_since` on a removed shot as a change.
- An edit made while Re-export is waiting is queued after the export and is not part of that wait.
- Safari may not blur a typed Length or prompt before the Re-export click, so that edit is not saved first. The tests run in Chromium only.
- `removed_in_run` relies on a field edit never landing in the same millisecond as the run's `submitted_at`. Edits are refused while a job is queued, and `_requeue` holds the job's write lock, so only an edit committed in the same millisecond just before an export could tie. The tie would read as re-cut, which is harmless.
