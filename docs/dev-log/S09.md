# S09 dev log: Starting a video writes a shot plan from the style text that the photographer can change

## Summary

Starting a video now creates a real draft job and plans it in the background. `POST /api/jobs` writes the `jobs` row (status `draft`, plan `planning`) and starts the planning job; the planner turns the style text and the shoot's photos into a shot plan; the plan is checked (movement names, lengths that fit the model's longest clip, total length within the song, photos in the shoot), asked for once more with the errors if it is invalid, and otherwise written to `job_shots` or failed with a reason. The photographer can re-plan from new text (`POST /api/jobs/{id}/plan`) and edit the plan (`PUT /api/jobs/{id}/shots`) before any money is spent. A job left `planning` when the app stopped is planned again on app start.

## Key decisions and assumptions

- The standing rule was no questions. Assumptions are listed here.
- Library.getStyle is not stubbed. The story lists it as a stub, but S03 had already landed it, so Jobs calls `library.service.get_style` and `list_songs` directly. S21 removes only the other three stubs.
- Providers.planShots has no parameter for the last plan's errors, so the retry appends them to the style text (`Your last plan was refused: ...`). The call site is one line in `planning.py` if S06/S21 prefer a dedicated argument.
- Any provider error, unparseable answer or invalid plan counts as one bad plan. The reason for a second failure is stored in `jobs.plan_notes`. Any other crash also fails the plan with its message, so a job is never left `planning` by an exception.
- Photos go to the planner with empty `jpegBytes`; small copies are wired by S21.
- Without a preset: fps 30, song offset 0, style name "Custom style". Photoshoots in `labelling` or `label_failed` are accepted; only `awaiting_upload` is refused.
- The plan length rule is each shot's length plus transition at most the model's longest clip, and the total length of shots with a photo at most the song minus its offset. Only the longest clip is checked, so 5 s on Veo (which makes 4, 6 or 8 s) passes; the video stage must round or reject.
- `updateJobShots` stores shots as sent (including `planNote`) and turns a failed plan into a ready one; positions are renumbered 1 to n in the order sent. `purpose: reproduction` is stored as sent.
- Criterion 3 is checked on the `jobs` row, because the shared `Job` type has no fps or song offset field and no shared type was changed.
- The first draft of the stage (plan POI 15) found that `stub_presets` leaves the reference job planning; fixed by inserting it as `ready`.
- PRD vs docs: no conflict found. The PRD starter-kit movement texts were used verbatim, including the PRD's literal `space,time-lapse` in Dolly In (timelapse).

## Found late and follow-ups

- S10 (submit and queue): make the draft and plan-status check part of the write in `store.replace_plan` / `set_planning` (409 `not_draft` / `plan_not_ready` inside the transaction), so a submit cannot land between the check and the write (CH-1). Same window exists between PUT shots and POST plan.
- S15 (plan screen): a hand-edited failed plan keeps the failure reason as `planNotes`; `planNote` is never set to `changed_by_photographer` by the server, so the client may need to send it.
- S21: remove `photoshoot_status`, `list_photos`, `plan_shots` and `allowed_lengths` from `app/jobs/stubs.py`; pass small photo copies to the planner; consider a dedicated errors argument on `planShots`.
- S07/S10: lengths are only checked against the longest clip, so the video stage must round or reject lengths the model cannot make (e.g. 5 s on Veo).
- Planning robustness (optional): clear reasons for a missing song and for a malformed planner answer (retry it), refuse or reset a preset offset at or past the chosen song's length, a per-job lock instead of the module-wide one.
- The deploy process test `tests/deploy/test_processes.py` is flaky when worktrees run in parallel.
- The story's `Stubs` line names Library.getStyle, which S03 already landed; the story text can be corrected.
