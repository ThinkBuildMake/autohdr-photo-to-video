# S28 - The worker tries each shot up to four times and switches model when one keeps failing

**Kind:** module (M) | **Blocked by:** S01 | **Review gate:** agents
**Status:** landed by agents (no human demo). Story gate green on the final run: 538 passed, 5 skipped.

## Summary

A clip that looks AI-made is never delivered. S28 builds per-shot steps 4 and 5 of the pipeline as `make_clip`: generate a clip, extract frames, check it, and record the attempt. A flagged or errored attempt is tried again, up to 4 attempts per shot per round (the first try plus 3 regenerations). When the video model refuses, or answers `failed` twice, the remaining attempts use the fallback model. A rate limit counts as an attempt and shows "Provider busy, trying again". Every provider error is written to the attempt before anything else happens. A shot whose attempts were all flagged is failed with `flagged_every_attempt`.

## What was built

All new files are inside the module boundary the plan set (S12 and S29 were building in parallel); no S12, S29, providers, media or files file was touched. Pipeline owns no table.

- `app/pipeline/clip.py`. `make_clip(job_id, shot, round_no, first_frame, prompt, requested_s, folder, earlier=())` runs one shot's attempts and returns the passed attempt's id, or None when the shot failed.
  - Attempts run from `shot.attempts + 1` to 4, so a resumed round only gets the attempts it has left. `AttemptLimitReached` ends the loop.
  - Per attempt: set the shot to `generating` ("Attempt n of 4: making the clip"), `start_attempt`, `generate_clip`, move the clip into the job folder, `extract_frames`, set `checking`, `check_clip`, store the clip at its key, `finish_attempt` (`passed`, `flagged` or `error`).
  - On any `ProviderError` (including a `MediaError` wrapped as `bad_response`), the very next call is `finish_attempt(..., 'error', error=e)`; the log line, model switch, busy detail and wait come after it. `out_of_credit` is recorded and then re-raised so the stop logic (S30) can end the job.
  - Busy answers (`rate_limited`, `timeout`) set "Provider busy, trying again" and wait `Retry-After` (default 5 s, capped at 30 s; NaN, negative or missing values use the default). No wait after the last attempt.
  - Fallback: a `refused` answer, or the second `failed` answer, from `generate_clip` switches the remaining attempts to `VIDEO_MODEL_FALLBACK`; the generating and checking details then name the fallback model. A refusal on the fallback fails the shot with `refused` at once. Busy answers, bad responses and check errors never switch the model.
  - Failure reason: `flagged_every_attempt` only when at least one attempt was flagged and none errored; otherwise `refused` or `provider_error` from the last error.
  - `earlier` replays the round's recorded (model, error kind) pairs so a resumed round keeps the fallback it had switched to.
- `app/pipeline/clip_stubs.py`. Stand-ins for Jobs (`set_shot_state`, `start_attempt`, `finish_attempt`, `set_shot_result`), Providers (`generate_clip`, `check_clip`), Media (`extract_frames`) and Files (`put`, in-memory bucket), with the architecture's signatures. S22 removes them. The file is not named `stubs.py` so it never collides with S12's.
- `tests/pipeline/clip_world.py`. Scripted test world: fake clock moved only by the busy wait, ordered event log, per-shot scripts for generate answers and checks.
- `tests/pipeline/test_clip_attempts.py` (AC1, AC2, AC5, AC6 and the QC-2, RL-1, FR-1.7 guards) and `tests/pipeline/test_clip_fallback.py` (AC3, AC4, fallback edge cases, resume cases).
- `docs/REQUIREMENTS.md`: the QC-2 requirement and decision rows now say 4 attempts per shot per round.

## Key decisions and assumptions

- **Orchestrator decision: 4 attempts per shot per round (the first try plus 3 regenerations).** REQUIREMENTS QC-2 said "regenerated up to 3 times" with the check "attempts <= 3" and "3 attempts" in another row. It was corrected to match ARCHITECTURE (attempt numbers 1 to 4), the HLD and the story. The PRD gives no number, so the PRD does not conflict with either reading.
- Every collaborator call goes through `clip_stubs`, so S22's swap to the real calls is mechanical.
- Attempt numbers and clip keys start at `shot.attempts + 1` (a resumed round writes `a2.mp4`, "Attempt 2 of 4") rather than at 1, so keys never collide.
- The same requested length is used on the fallback (Veo's 4/6/8 s sit inside Seedance's 4 to 15 s) [assumed].
- A Retry-After of 0 waits 0 s instead of the 5 s default.
- `attempts.cost_usd` records the clip cost; the check's cost stays in its `provider_calls` row, so job totals are unaffected.
- S29's `finish_attempt` also writes a busy detail; S28 additionally sets "Provider busy, trying again" (the architecture's wording). Harmless duplication.
- PRD vs docs: the PRD gives no attempt count or fallback model, only that video must not look AI-made, which the check-and-retry loop serves. No place where the PRD overrode the docs or wireframe.

## Found late / follow-ups

- **S22 runner must pass `make_clip(earlier=...)`.** Nothing in `app/` calls `make_clip` yet. The runner hook (replace `prompt.request_clip(...)` in S12's `_run_shot` with `clip.make_clip(...)`) is done by S30 or S22, whichever edits `runner.py` first after S12 and S28 are both integrated. The hook must pass the round's recorded attempts as `earlier`, otherwise the resume protection for the fallback model has no effect. S22 also folds `clip_stubs.py` into the real Jobs, Providers, Media and Files calls and deletes it.
- **The resume replay cannot tell a check error from a generate error.** `earlier` carries only (model, error kind), so a recorded `failed` or `refused` from the check stage switches the model on replay, although live only generate errors switch it. An earlier refusal on the fallback also continues to another attempt instead of failing `refused`.
- **The failure-reason rule ignores attempts made earlier in a resumed round.** The `flagged and not errored` test looks only at attempts run in this call, so a resumed round whose earlier attempts errored can still report `flagged_every_attempt`, and a resumed shot with 4 attempts already used always gets `provider_error`. This affects only the shots-dropped metric on resumed jobs.
- An attempt is left open and the shot without a result if something other than `ProviderError` or `MediaError` is raised (for example from `shutil.move`, `put` or `finish_attempt`); leave to the runner's per-shot handler.
- A clip whose check errored is not stored (`clip_key=None`), though the architecture says every attempt's clip is stored.
- `JobShot` carries no round, so `round_no` comes from the caller. The deadline check before each attempt (S30) belongs at the top of the attempt loop.
- KEY_METRICS, STACK and HLD still say "up to 3 regenerations"; this agrees with 4 attempts, so no change is needed.
